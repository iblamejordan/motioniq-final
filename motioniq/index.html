AI-Powered Human Activity Intelligence

“Understanding human movement through artificial intelligence.”

A phone's accelerometer and gyroscope record how it moves, hundreds of times per minute. MOTIONIQ trains a machine-learning model to read those signals and decide whether the person carrying the phone is walking, climbing stairs, sitting, standing or lying down.

01 · Project overview

What MOTIONIQ is

MOTIONIQ is an AI-powered human activity recognition (HAR) system. It takes motion measurements from a smartphone and turns them into activity labels, simple statistics and charts.

The full title is AI-Powered Human Activity Recognition and Intelligence System Using Smartphone Sensors. It is built as a university AI/ML mini-project.

▼
AIMachine-learning classifierLearns patterns that separate one activity from another

Why it was developed

Smartphones already carry motion sensors, but the readings are just streams of numbers. The project explores how machine learning can give those numbers meaning, as a practical way to learn the full AI/ML workflow: data, features, model, evaluation and interface.

How smartphones collect movement data

An accelerometer measures how quickly the phone's speed changes along three axes (including the pull of gravity). A gyroscope measures how fast the phone rotates around those axes. Sampled repeatedly, they give a record of motion.

How AI interprets it

Short windows of signal are summarised into numeric features. A classifier trained on labelled examples learns which feature patterns belong to which activity, then predicts the label for new, unseen windows.

What the final application aims to achieve

A dashboard that shows the predicted activity, an activity distribution, movement patterns, a daily summary, an activity history and a warning for prolonged inactivity. Planned

02 · Problem statement

Raw sensor data does not explain itself

Understanding and monitoring physical activity by hand is slow, subjective and hard to repeat. Motion sensors record everything, but recording is not understanding.

The problem

  • Uninterpreted sensor data. A stream of x, y, z values does not tell a person what they were doing.
  • Hard to identify activities manually. Reading signal plots by eye is slow, inconsistent between people, and impossible at scale.
  • No automatic classification. Without a model, nothing turns each time window into a label.
  • No meaningful analytics. Time spent per activity or long stretches of inactivity cannot be reported from raw numbers.
illustrative raw readings (not from a dataset):
0.01, -0.98, 0.12   0.03, -0.97, 0.10   0.21, -1.04, 0.33 …
→ which activity is this?

Why an AI-based solution helps

  • Learns the patterns. A model finds regularities in labelled data that are hard to write as hand-made rules.
  • Consistent and automatic. The same input always gives the same prediction, for any number of time windows.
  • Measurable. Accuracy, precision and recall show how good the classifier actually is, and where it fails.
  • Enables analytics. Once every window has a label, counting, summarising and flagging inactivity becomes simple.
03 · Project objectives

Eight things the project sets out to do

  1. Recognise activities automaticallyClassify each time window into one of six activities without manual labelling.
  2. Analyse sensor measurementsStudy accelerometer and gyroscope signals and what distinguishes activities.
  3. Develop a classification modelTrain and compare machine-learning classifiers on labelled data.
  4. Display predictions in an interfaceShow the predicted activity through a simple dashboard.
  5. Generate activity statisticsSummarise how much time was spent in each activity.
  6. Visualise movement patternsPlot sensor signals and activity distributions so patterns are visible.
  7. Identify prolonged inactivityFlag long stretches of low-movement activity in recorded results.
  8. Evaluate model performanceMeasure accuracy, precision, recall, F1-score and the confusion matrix.

    05 · Activity recognition

    Six activities, from the UCI HAR dataset

    The classifier chooses one of six labels. Three involve walking-type movement; three are static postures.

    Walking

    Dynamic

    Steady movement on level ground, producing a regular, repeating pattern in the sensor signals.

    Signal idea: periodic acceleration changes with each step.

    Walking Upstairs

    Dynamic

    Climbing stairs, a walking motion with an extra upward effort on every step.

    Signal idea: similar to walking, so it can be confused with it and with walking downstairs.

    Walking Downstairs

    Dynamic

    Descending stairs, with a different impact and rhythm on each step than climbing.

    Signal idea: periodic, with step impacts that differ from level walking.

    Sitting

    Static

    Seated and mostly still. Very little movement, with the phone held at a particular tilt.

    Signal idea: low variation; can resemble standing because both are still.

    Standing

    Static

    Upright and mostly still, with the phone at a different orientation from sitting.

    Signal idea: low variation; separating it from sitting relies on subtle orientation cues.

    Laying

    Static

    Lying down. Gravity acts along a different axis of the phone than in the upright postures.

    Signal idea: still, with a clearly different gravity direction.

    “Signal idea” lines are qualitative explanations of what to expect, not measured results from this project.

    06 · Dataset and data processing

    The UCI Human Activity Recognition dataset

    MOTIONIQ uses the public Human Activity Recognition Using Smartphones dataset from the UCI Machine Learning Repository. It contains smartphone sensor recordings labelled with the six activities above.

    Accelerometer

    Measures acceleration along three axes (x, y, z). Because it also feels gravity, it reveals how the phone is tilted as well as how it moves.

    Gyroscope

    Measures angular velocity: how fast the phone turns around each axis. It captures twisting and swaying that acceleration alone can miss.

    Train and test data

    The dataset is distributed already divided into a training set (used to fit the model) and a test set (held back to evaluate it on unseen data).

    07 · Machine-learning architecture

    Random Forest first, then compare

    The initial algorithm is a Random Forest Classifier. Decision Tree and Support Vector Machine are discussed as comparison models.

    Why compare algorithms?

    No model is best for every dataset. Training several on the same data and scoring them the same way shows which one actually performs better here, instead of assuming.

    What a fair comparison needs

    The same train/test split, the same preprocessing and the same metrics for every model, so differences come from the algorithm and not from the setup.

    Current status

    Random Forest has been tried in a preliminary experiment. Decision Tree and SVM comparisons are Planned unless you update this note after running them.

        10 · Results and model performance

        How the model will be judged

        The model is evaluated on the held-out test set, using the measures below. Verified numbers have not yet been entered, so placeholders are shown instead of invented figures.

        Accuracy

        —

        Share of all test windows labelled correctly. Easy to read, but it can hide weak classes.

        Precision

        —

        Of the windows predicted as an activity, how many truly were it. Reported per activity.

        Recall

        —

        Of the windows that truly were an activity, how many the model found. Reported per activity.

        F1-score

        —

        Balance of precision and recall in one number, per activity.

        Confusion matrix

        Placeholder · not real data

        Rows are the true activity, columns the predicted one. Correct predictions sit on the diagonal; off-diagonal cells show which activities get mixed up.

        To publish verified results
        1. Open the saved Random Forest experiment and re-run the evaluation on the UCI HAR test split.
        2. Copy accuracy, the confusion matrix and the per-class report into js/results.js.
        3. Set verified: true. The page then shows real values and animated counters automatically.
        11 · Limitations

        What this project cannot yet do

        Data

        Dependence on sensor-data quality

        Noise, dropped readings or a different phone placement change the signals and can mislead the model.

        People

        Individual movement differences

        People walk, sit and climb stairs differently. A model trained on some people may perform worse on others.

        Scope

        Limited initial activity categories

        Only six activities are recognised. Anything else, such as running or cycling, will be forced into one of the six.

        Data

        Dependence on the available dataset

        The model only knows what the dataset showed it. Conditions outside the dataset are not guaranteed to work.

        Deployment

        Real-time collection

        Streaming live phone data brings sampling, permissions, battery and latency challenges that the dataset-based work does not address.

        Model

        Prediction errors

        No classifier is perfect. Similar activities, such as sitting and standing, are the usual place for mistakes.

        13 · Conclusion

        Giving motion data a meaning

        MOTIONIQ shows, end to end, how machine learning can turn raw smartphone sensor readings into activity labels and useful summaries. It follows the standard AI/ML workflow: a public labelled dataset, preprocessing and features, a trained classifier, measured evaluation and an interface to present the outcome.

        The project is still in progress: results are being verified, comparison models are planned, and the dashboard is a preview. That is the honest state of the work, and the structure is ready for real numbers to be added.
